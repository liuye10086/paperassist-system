## 1. 结论与使用方法

采用“按模块分阶段，每阶段数据库 → 后端 → 前端 → 验收”的顺序，覆盖下列各模块的全部功能点。现有小闭环的应用与测试底座已统一到 PostgreSQL，旧数据已完成切换；当时后端289项和前端78项回归通过，历史证据见迁移记录。登录交付时后端全量313项通过（182.76秒）、前端96项通过，保留其独立交付记录中的历史边界；本轮项目编辑的359/115项结果另记。后续沿用这一底座扩展文件、分析、文献、写作和修改能力，不再以 SQLite 作为运行或测试数据库。不要先一次建完所有未来业务表，也不要等所有后端完成后才开始前端联调。

- `- [ ]`：尚未完成验收；包括已有原型、但仍需要迁移或扩展的功能。
- `- [x]`：该条已在写明的范围内确认；历史验收和本轮检查分别说明。
- `S04-BE01` 等编号：阶段、层次、条目；后续讨论、提交和验收引用该编号。
- “建议 / 待决策”：尚未由用户定案，不能直接当作获准的新产品功能。
- 所有阶段继承阶段00的数据边界、权限、预算和外部服务限制。
- 每阶段先完成所依赖的决策，再实施对应条目；其他不依赖该决策的条目可继续。
- 完成条目时记录实现文件、验证命令或人工样例、结果与限制，再勾选；已有代码不能代替验收。
- 本目录只保存路线与阶段任务清单；实施计划、迁移及验收记录放入 `docs/开发记录/阶段NN/`，跨阶段台账放入 `docs/开发记录/项目管理/`。入口与归档规则见[文档导航](../README.md)。
- 执行阶段可用 `subagent-driven-development` 或 `executing-plans` 逐项推进；开发进度以条目对应的实际验证证据为准。

这些是功能级清单，按用户要求不展开完整实现代码。具体接口 Schema、迁移字段和测试样例在对应模块开工时细化，涉及不兼容重构时先提交方案给用户决定。

## 5. 统一开发规则

- 持久化先确定资源归属、不可变版本、外键、索引和迁移，再开发服务和页面。
- 应用与测试只使用 PostgreSQL；迁移显式执行，启动/健康检查不执行 DDL。测试只使用专用库和本例生成的 schema，禁止通用连接变量或 SQLite 回退。
- 接口先明确输入、输出、错误和权限；沿用 `/api/v1`，已有接口迁移需保持闭环或提供明确兼容方案。
- 共享解析、统计、文献、写作、导出和修改引擎，不为 SCI 与毕业论文复制两套逻辑。
- 小文件先按现有代码结构迭代；新目录属于建议，不借文档一次重写整个后端。
- 保留用户已确认的 Code Interpreter 云端绘图；新增统计方法的执行位置单独评估。
- OpenAI 图片生成属于已确认的后续独立能力，具体用途仍待确定；不能代替真实统计图或生成实验结果证据。
- 功能完成必须同时覆盖权限、来源版本、语言、错误/等待状态、历史恢复和下载关联。
- 需求不清时提交“问题、推荐方案、备选、影响模块、最迟决定时间”，不得悄悄扩范围。
- 每次完成后汇报修改、验证和限制；提交、推送均须用户明确确认，不将完成开发或验收视为获准提交。
- 本机验收通过 `script/dev.cmd start|stop|status` 管理后台前后端；用户确认验收完成后先停止服务，再按明确授权的提交信息提交推送，之后等待用户确认下一步。
