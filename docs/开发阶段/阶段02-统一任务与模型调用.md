## 范围与现有基线

既有小闭环已保存绘图及解释的云端请求、任务状态和结果；本阶段重点是迁入统一任务契约，保留项目、输入版本、云端响应标识与成果。当前Word、新绘图和新解释已接入Celery/RabbitMQ；两类模型任务使用统一调用/用量记录及三级累计预算。历史绘图和解释仅兼容读取/续取，不补造历史账本。项目任务列表、详情、事件、三级预算及持久待办/原子恢复已交付；LangGraph和工作流检查点尚未实现。

绘图继续使用用户已确认的 OpenAI 官方 Responses API + 托管 Code Interpreter。本地描述统计保留为独立核对依据；不在宿主机执行模型生成代码，不改为本地重新绘图。GPT Image 是后续独立能力，本阶段仅预留适配接口和用量类别，不以其替代统计图。收费账本、支付和退款仅在用户确认收费范围及规则后于阶段10实施，不作为本阶段或基础发布的必选项；本阶段处理供应商实际用量、内部估算与预算控制。

已确定并实测Celery 5.6.3 + RabbitMQ 4.3.6的Linux容器执行基线，现有原生Windows API/Vite及PostgreSQL保留；PostgreSQL业务记录为用户任务状态依据。采用普通AMQP依赖，避免Kombu的SQLAlchemy extra与现有SQLAlchemy 2.1.1约束冲突；不启用Celery结果后端。LangGraph待实际多步骤需求出现时再引入，当前尚未安装。运行与隔离细节见[Worker说明](../../infra/worker/README.md)。

本阶段目标是约束自身记录与副作用的幂等；Word、新绘图及新解释已有重复投递、明确恢复及真实硬退出验证。模型轮询释放Worker并保持同一attempt；提交开始后结果未知时保留预留且不自动重发，有响应标识只续取。绘图分别保存创建容器、上传材料、提交响应的开始标记和回执，并用本地PNG候选恢复发布。恢复请求已增加持久幂等回执、代次和输入版本核对；此本地约束不能承诺外部模型调用严格“恰好一次”。资料补充与研究计划确认尚无实际业务消费者，兼容待办只读展示。

## 用户状态与内部字段映射

需求 V0.13 §9 的十种用户状态按下表统一映射。`status` 表示生命周期，`phase` 表示处理阶段；用户状态由二者推导，不再维护第三套独立终态。先判断等待或终态，仅在 `running` 时按 `phase` 显示执行阶段。

| 需求中的用户状态 | `status` | `phase` 与展示规则 |
| --- | --- | --- |
| 待执行 | `queued` | 保存预计起始阶段或上次阶段，显示待执行 |
| 文件解析中 | `running` | `parse` |
| AI 分析中 | `running` | `plan`、`interpret` 或 `verify`，阶段详情区分计划、解释和核查 |
| 数据计算中 | `running` | `compute`，包含真实统计和按数据绘图 |
| 文献检索中 | `running` | `search` |
| 文档生成中 | `running` | `write` 或 `export`，阶段详情区分章节生成与文件导出 |
| 待补充资料 | `waiting_input` | 保留暂停时阶段，展示待补材料而非继续执行中 |
| 待用户确认 | `waiting_confirmation` | 保留暂停时阶段，展示待确认内容 |
| 已完成 | `succeeded` | 保留最后阶段，显示完成及成果入口 |
| 执行失败 | `failed` | 保留失败阶段，显示失败原因与允许的下一步 |

`interpret` 已用于新解释任务；以上映射已用于内部契约和任务API。Word、绘图、解释卡片及项目摘要已接入相应排队、执行、等待和终态，统一任务页已实现十种状态映射并经自动测试；当前真实业务仍只有绘图、解释和Word，不能把解析、计划或检索的映射视为对应执行能力已实现。取消状态如获准再扩展，不能挤占这十种必需状态。投稿、返修、录用和评审通过仍是独立项目进展。
