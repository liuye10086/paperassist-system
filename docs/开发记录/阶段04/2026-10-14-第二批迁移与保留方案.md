# 阶段04第二批增量迁移与保留方案

当前为实施方案；实际执行结果另见本批交付记录，不以本文件证明已升级或已验收。

## 精确结构变更

由 `0024_research_plans` 升至 `0025_correlation_planning`：

1. `tasks_type_check` 在原任务类型集合中增加 `analysis_recommendation`。
2. `tasks` 末尾新增可空 `verification_failure JSONB`，既有行保持 `NULL`，不回填。
3. 新增 `tasks_verification_failure_check`，只允许 `NULL` 或 JSON 对象。

不新增业务表、索引，不改旧主键、来源、任务、决定、检查点、结果 JSON 或费用数据。相关计划和结果使用已有版本化存储；失败证据列保存受限差异与回执，不保存外发逐行数值。

预计业务结构由40表、381列、130索引变为40表、382列、130索引。这是预期差异，不是迁移后实测结果。

## 执行与保留核对

- 独立审查增量迁移及执行脚本，冻结源码 SHA256；执行前逐文件重核，防止审查后变化。
- 确认开发 API/Vite/Worker/dispatcher/RabbitMQ 停止；定位本机 `paperassist_system` / `public`，禁止测试库或远程库混用。
- 用所有业务表旧列指纹、索引清单和30个原资产核对本批开工只读基线。若用户期间新增业务资料导致基线变化，停止迁移并重新核查，不覆盖变化。
- 在一致性 PostgreSQL 快照与表锁下创建 custom-format 数据库备份，检查 `pg_restore --list` 中每表数据项及备份文件哈希；同时保存资产副本/哈希、结构与旧列指纹、审查源码和执行记录。保留原有全部备份。
- 在同一事务内执行 Alembic 升级；提交前核对精确列/约束差异、旧列投影指纹、全部索引、资产与只读审计。增加空列造成的全行 JSON 差异不能替代旧列投影核对。
- 提交后使用运行账户再次只读核对同一内容及权限。只有全部通过才启动验收服务。

备份目录为 Git 忽略的 `backend/backups/correlation-planning-<timestamp>/`；本机执行证据保留于 `script/.runtime/stage04-batch02/`。这些目录不是可移植源码，其他机器需重新检查实际状态。

## 失败处理

提交前出错由事务回滚，保留备份与失败记录；提交结果不明确时只读查明，不自动还原或重建。提交后核对失败停止交付，不静默覆盖数据。

迁移的降级保护会拒绝删除已存在的推荐任务、v3计划、相关结果或失败证据；本批不执行降级。备份目录与清单核验不等同于在另库实际恢复演练，未做恢复演练时明确记录。

本方案不勾选阶段04原清单，不提交、不推送。
