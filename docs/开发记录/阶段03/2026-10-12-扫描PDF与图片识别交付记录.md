## 本步交付范围

- `.xlsx / .docx / .pdf / .png / .jpg / .jpeg` 共用批量上传；每文件10 MiB、每批10项、上传并发2。JPG归一为内部 `jpeg` 类型，文件名及原件字节不改。图片上传自动提交OCR，支持重新识别；只支持静态PNG/JPEG，图片最多20,000,000像素。
- PDF仍限定未加密、最多100个物理页，上传及“重新提取文本”继续使用原文本解析链。新增“识别所选页”：每次选择1—10个唯一物理页，建议无可提取文字的页，也允许手工选择已有文字、错误隐藏层或混排页。OCR版本只覆盖所选页，不自动合并或替换文字层。
- 本机Linux Worker通过独立受限进程识别中英文印刷体及数字/单位，保留原始识别字符串、置信度、四边形位置和来源坐标。每条文字固定为 `unreviewed`，低于0.8提示较低置信度，高分也不会自动确认。没有文字是有效空结果，与损坏文件、进程失败、资源超限分别处理。
- 新增独立 `ocr_document` 合同，沿用文件、`file_parse_results`、`parse_file`任务、统一版本序号、幂等、版本锁与租约发布。快照冻结原件版本/哈希、选页、模型及精确配置；失败不覆盖成功版本，父Worker失联按原有租约整次重跑，只发布完整结果，不提供逐页续跑。
- PDF页用PDFium从200 DPI逐页渲染并释放资源，每渲染页最多12,000,000像素。图片仅作EXIF方向和RGB白底标准化并记录变换，不改原件。派生JPEG核对图最长边1600，文字框保留完整识别像素坐标；PDF另外保存原页points、bottom-left坐标约定及映射，图片保存到原像素的逆变换。
- 文件详情按所选版本 `kind` 展示Word结构、PDF文本或OCR页面；OCR页序号与真实物理页号区分，文字按20条分段。鉴权Blob加载核对图，点击文字突出对应位置框；保留原件和结构JSON下载、失败后旧版本读取、中英界面提示。分析入口仍只列Excel。

本步不包含手写承诺、公式结构、扫描表格数据集、图表数值反推、直接统计、OCR人工编辑/确认、Docling对比或外部视觉调用。没有更改真实模型配置、付费预算或调用外部付费模型。

## 整合中发现并修复的问题

**新增NumPy影响旧Excel子进程。** 真实混合队列及浏览器初始数据准备暴露Excel `parse_environment_unavailable`，OCR/Word/PDF已成功。空环境下openpyxl因NumPy存在而导入BLAS，实测16线程、VMS742,972 KiB，违反原单线程检查且超过旧512 MiB地址空间。仅在预览和完整结构两个Excel bootstrap的依赖导入前强制六个原生线程变量为1，保持30秒CPU/512 MiB/60秒墙钟及原沙箱。真实Linux预览12项通过、1项Windows-only跳过，完整结构3项通过；双bootstrap回归测得1线程、VMS约149,604/149,672 KiB。Windows相关49项通过、14项跳过。此后root重建生产镜像，真实混合队列完整两项已通过。

**READY前资源错误被误分类。** OCR预热内存不足原本发 `parse_resource_limit`，共享runner只允许启动环境错误，导致被改报 `parse_output_invalid`。最小补丁只加入该固定资源错误信封，未知代码及额外字段仍拒绝，发送用户字节仍必须先收到READY。真实短子进程测试通过 `select(stdin)` 验证未提前发送payload/EOF，并核对OCR调用者收到正确错误码。它验证协议传播，不冒称实际耗尽了模型预热内存。

Worker构建还出现过公共包源read timeout，`pip install --timeout 60`修复下载等待；不改变任何运行预算。初始失败日志保留，没有把构建失败当作业务解析失败。
