## 本步交付

1. Windows 原生 API/Vite/PostgreSQL 保留；Linux 容器运行 RabbitMQ、Celery Worker 和 outbox dispatcher。只安装普通 Celery，不使用 SQLAlchemy extra、Celery 数据库结果后端、Redis、Beat 或 LangGraph。PostgreSQL 任务记录是状态依据，API 只写任务，不在请求内生成 Word。
2. 沿用 `/report` 路径：POST 校验现有来源并入队，接受 `Idempotency-Key`，省略时由确定的来源引用产生稳定键；返回202及 `task`，已有完整报告返回200。GET 只读并返回对应任务，原下载地址保持。失败任务通过 `POST /api/v1/tasks/{id}/retry`、`expected_revision` 显式重试；该失败修订号本身作为恢复操作的唯一标识，重复请求复用已记录的 requeued 事件，不再次产生 Attempt。
3. Worker 只注册 `word_report`。数据库短事务领取、租约及心跳；渲染和消息发送在数据库事务外。重复消息/旧修订号不可重复领取；心跳不增加任务修订号。完成时再次校验租约、账户、项目归属、当前配置和源文件，报告记录与成功状态、Attempt、事件同事务提交。
4. 沿用报告按解释和模板唯一的约束。任务专属稳定成果候选 ID、Attempt 专属暂存文件；旧 Worker 不能提交或删除新成果，提交结果未知时不盲删最终文件。保留历史下载和原来源变更拒绝语义。
5. outbox 至少一次投递、持久队列/消息、发布确认；确认后才标记已发送。数据库租约过期扫描支持有限自动恢复（最多3次自动执行机会），最后失败可由用户显式重试；普通来源错误不自动重试。队列停机不丢数据库中的已接受任务。
6. `0007` 增加任务成果引用、安全错误码及租约扫描索引，不新增通用工作流平台。Word 卡片显示排队、生成、失败和重试，刷新后读回任务；项目摘要显示这些任务并避免重复显示其报告完成记录。仅锁 Word 提交动作，不因后台任务锁住工作台。

## 实施前核查（历史）

实施前已核查：Celery 5.6.3 支持 Python 3.11，Kombu 的 SQLAlchemy extra 约束与当前 SQLAlchemy 2.1.1 不兼容；本方案不使用该 extra。当时Docker/Compose可用但引擎未启动；宿主PostgreSQL可用，HBA只有loopback，尚需实测容器连接。

当时待实测：Linux镜像依赖、真实投递与故障恢复、宿主连接来源及文件挂载、完整回归。后续实际结果已记入上方交付记录；本机最终无需修改HBA或防火墙。
