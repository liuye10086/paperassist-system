## HTTP 与重试契约

- `POST .../analysis-runs/{run_id}/report` 保留 `expected_revision`、`figure_id`、`explanation_id` 请求体，接受可选 `Idempotency-Key`。省略时按来源引用生成稳定键；相同键绑定相同输入复用任务，冲突返回409。已有完整报告优先按原约束复用。
- `GET .../analysis-runs/{run_id}/report` 返回只读报告状态及对应 `task`，不创建任务、不推进执行。原报告下载权限、完整性检查和历史版本地址保留。
- `POST /api/v1/tasks/{task_id}/retry` 仅允许本人失败的 Word 任务，请求体为 `{ "expected_revision": 当前失败任务修订号 }`，并检查会话及CSRF。该失败修订号与已记录的重新排队事件构成重复重试回执；同一次操作重提不会再次入队或增加Attempt。这不等于通用等待态恢复幂等协议。
- 任务详情/事件接口及新Word POST提供服务器生成的 `X-Request-ID`；错误保留 `detail.code/message/params`，增加 `request_id/details`。原Word GET和下载的错误正文未整体改造。
- 公开任务可返回安全的 `result_report_id/error_code`，不返回原始输入快照、幂等键、租约令牌、文件路径或秘密；界面不直接展示这些内部标识。

普通来源错误和权限错误直接失败，不自动重试。有限自动恢复只针对租约过期，最多总计3次Attempt；用户明确重试仍可获得一次执行机会，达到上限后该次执行再丢失不会继续自动循环。outbox发布失败采用持续退避；Worker暂时无法访问数据库时延迟后重新入队，不能概括为“所有错误均有限重试”。

## 兼容性、本机运行与测试隔离

已实测的版本为 Celery `5.6.3`、Kombu `5.6.2`、RabbitMQ `4.3.6-alpine` 和 Python `3.11.17-slim-bookworm`；容器基础镜像按digest固定。只安装普通AMQP依赖，不安装与现有 SQLAlchemy `2.1.1` 约束冲突的 Kombu SQLAlchemy extra。没有引入Redis、Beat、Flower或Celery结果后端。LangGraph继续暂缓，待真实多步骤需求再决定接入。

RabbitMQ 4.3真实联调发现临时非独占控制/事件队列不兼容，已显式配置 Celery `control_queue_exclusive`、`event_queue_exclusive` 并复验，没有开放broker弃用功能。Worker为Linux prefork、并发1；这一结果不证明生产容量或多Worker压力已经验证。

容器经 `host.docker.internal` 访问现有PostgreSQL，本机实测连接来源为loopback，无需修改HBA或防火墙。RabbitMQ不发布宿主端口。启动器仅提取运行库及broker所需配置，秘密保存于Git忽略且限制访问的本地运行目录；不挂载 `.env`、模型密钥或迁移凭据。完整运行命令见[Worker说明](../../../infra/worker/README.md)和[脚本说明](../../../script/README.md)。

默认自动测试使用专用PostgreSQL测试库、每例UUID schema和临时资产，不连接开发队列、不使用Celery eager代替真实执行。`script/test-queue.cmd` 显式运行真实队列测试，每次建立独立Compose项目、broker/卷、vhost、队列、测试schema及临时资产；结束后清理本例测试资源。真实队列测试未写开发任务、未调用模型。
