### 3.1 固定交付合同与验收记录

快照归属于现有 `delivery_id`，保存 `stage=first|revision|final`、父快照、期望修订号、需求版本、明确的修改说明及意见轮次。稿件成员固定 root/version/export、presentation、语言/审阅模式；报告/图成员固定 version/member；已有补充文件固定文件身份及 SHA。客户端只提交这些标识，实际归属、成功状态、路径、大小和 SHA 由服务器现有服务读取，不接受任意本地路径或客户端自报哈希作证明。

首次可保存已交付范围及明确待补项；修订记录新增/替换/移除成员与原因；最终阶段仍区分“已齐套”“缺必需成员”“有未决质量项”。缺必需 PDF 等允许保存缺口清单、下载已有成员，不能把该版本标为最终齐套。需要补齐时另存新快照；不自动改旧清单或用新成员替换旧包。是否齐套按固定本次需求判断，不强制所有交付都必须包含不存在的分析/图源。

验收采用独立追加事件，绑定快照 ID/SHA、操作者、时间、明确接受范围/保留项和意见。任务成功、文件齐全、选择 `final` 均不自动等于客户验收。产品只能记录当前有权用户的明确操作/所提供客户回复，不伪装为客户亲自登录；纠正接受记录也追加说明，不删除原记录。W2 当前聊天验收留在 W2 记录中，不迁造为 W3 产品验收。

新持久化只承载交付快照与验收事件这两类事实；异步封包沿用 task/attempt/lease/checkpoint 和既有产物存储。新增任务类型接入原分派、恢复和发布约束，不能仅靠一次脚本跑通后绕过正常入口。历史交付不依赖“当前最新”稿件/图指针；已失效或缺失的实际源文件按原权限/完整性规则报告，不以缓存掩盖。

### 3.2 成员清单、图源声明与统一 ZIP

- 同一个快照内只接纳同 owner/project 下、符合交付类型的精确成功成员；不同项目或不同实验结论不能拼成同一研究。SCI 与学校登记可各自引用同项目共有来源，但有各自独立交付快照。
- 冻结稿件图号/表号与实际成员及面板的对应关系；明确用户确认的图号，无法证明对应时列待核对，不靠文件排序猜配。相同科学图有不同语言派生时，保留共同图身份和各自文件版本。
- 每图列实际像素、声明及可测 DPI、物理尺寸、面板顺序/标签、文件格式、图注、已有绘图脚本/配置/数据的位置。SVG/PDF 内含位图须明确说明；DPI 缺失不能默认为300。图中文字未知、字体或语义未验状态从来源继续传递。
- 按现有 ZIP 规则组织 `manuscripts/`、`reports/`、`figures/`、`tables/`、`reproduction/` 等有限目录，附 `delivery.json`（交付快照）、`changes.json`、材料/限制说明及原格式 `manifest.json`、`SHA256SUMS.txt`。只列实际成员，不为缺件放空文件。
- 已有完整报告 ZIP 可作为一个固定成员原样纳入，并列出其内层 manifest 身份和成员索引；无需解包后再复制一套 XLSX/原图。只有本次明确选择单件方便下载时才提供对应成员，不让默认包重复塞多份相同内容。
- 实际封包、发布和下载边界保留必要的字节/来源/权限核对；同一阶段对同一已规范化成员复用现有验证证明，避免逐成员重新遍历同一个全报告闭包。打包只读已有结果，不调用分析、模型、绘图或文档转换。
- **普通完整交付与盲审子交付分别冻结。** 盲审 DOCX/PDF 不足以证明原报告 ZIP、Excel、图源/代码、文件名和 manifest 已匿名；原始材料不能自动混入盲审包。盲审成员只选已明确适用的派生件，内部 owner/project 定位不写入对外盲审清单，必须保留而尚未处理的成员列缺口。没有证据不宣称整个 ZIP 匿名；不扩建通用脱敏平台。
- 原始资料和有许可限制的材料按既有使用边界处理：能分发才嵌入；否则记录精确版本/获取说明，不能因为进入 ZIP 就新增下载或转授权。

### 3.3 产品入口与有界进度改进

在现有“交付登记”提供选择已有成员→核对缺件/规格→冻结快照→创建/恢复封包→鉴权下载→记录接受的闭环。研究报告、稿件导出页提供进入该登记的固定深链，不复制一套成果管理页。草稿、请求键和异步任务继续使用既有模式；响应未知时读回原请求/任务，不再次 POST 新任务。

新封包显示真实阶段：冻结输入、来源核验、整理已有成员、写包、发布。现有报告任务只在其确实执行的源码接点补来源核验/表图/文档/PDF/封包阶段；不能把心跳计数当百分比，不能在 W3 复用旧文件时显示“重新生成中”。使用原 checkpoint/事件和阶段结束时的统计，不逐表行写进度、不重复扫描数据计数。

性能事实：B05 已保存最后封包耗时 `1958.712673s`（约32.6分钟）；进程累计读取计数不是单任务性能基准。本轮静态核查发现 `ResearchReportService.member()` 会核对全部成员后再次读取目标，W3 若逐项调用容易重复工作。这是**局部优化候选，不是已证明的主耗时根因**。优先在一个现有 phase 内读取本次选中成员；用小型固定输入统计完整读取次数与输出 SHA，能证明相同校验语义且减少读取才落地。否则只交付进度并保留慢的限制，不重跑长报告验证它仍慢，不承诺性能 SLA。
