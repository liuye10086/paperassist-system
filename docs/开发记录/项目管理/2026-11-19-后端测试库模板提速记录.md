# 后端测试库模板提速记录

2026-11-19 · `feat/workflow-ui-redesign` · 用户要求立即实施，并留好记录以便回退。只改测试设施，不改产品代码。

## 一、原因

`tests/conftest.py` 的 `postgres_schema` 是 autouse 夹具。每条测试都新建一个 `pa_test_` schema，再从头执行全部迁移（当前头为 `0090_material_submissions`）。实测单条测试的准备时间约 8.7 秒，而测试本身大多不到 2 秒。一个测试文件因此要跑 1–6 分钟，B02–B04 的后端线几乎都在等这一步。

## 二、改法

| 文件 | 改动 |
| --- | --- |
| `backend/tests/schema_template.py`（新增） | 每个 pytest 会话只建一次模板 schema：真实执行 `migrate_database`，然后 `pg_dump --schema=<模板> --no-owner --no-comments` 一次，把 SQL 文本缓存在内存里。之后每条测试把文本中的模板名替换为本测试的 schema 名，用 `psql --single-transaction -v ON_ERROR_STOP=1` 载入。载入后核对：关系数、函数数、触发器数、Alembic 头，都必须与模板一致 |
| `backend/tests/conftest.py` | 清理改为调用 `schema_template.drop_schema`：先整体删除，遇锁上限再分批删表。`postgres_schema` 先调用 `schema_template.clone(...)`。克隆失败、未装 `pg_dump`/`psql`，或设置了 `PAPERASSIST_TEST_SCHEMA_TEMPLATE=0` 时，走原来“建 schema → `migrate_database`”的路径，代码原样保留。清理（`DROP SCHEMA`）和 `register_new_test_schema` 都不变 |

要点：
- **模板名由迁移内容决定**：模板名是 `pa_test_` 加 `alembic/versions` 下全部 `.py`、`.sql` 文件内容的 SHA-256 前 32 位。改了或新增迁移，模板名就会变，自动新建模板，不会用到过期的模板。
- **克隆内容完整**：克隆包含表、序列、函数（含 0080、0081 中写死 schema 名的函数体）、触发器、种子数据和授权（`GRANT`）。实测 550 个关系、103 个函数、133 个触发器与模板完全一致。
- **模板不清理**：模板 schema 在测试库里长期保留，供下一个会话复用；迁移变化后会产生新模板。旧模板可以按第五节手动删除。

## 三、实测

| 指标 | 原来 | 现在 |
| --- | --- | --- |
| 单条测试准备时间 | 约 8.7 秒 | 约 2.7 秒 |
| 会话中第一条测试 | 约 8.7 秒 | 约 24 秒（迁移一次加 `pg_dump` 一次，每个会话只发生一次） |
| 结果对照 | 见第四节 | |

## 四、正确性对照

同一组测试文件先后跑两遍：一遍设 `PAPERASSIST_TEST_SCHEMA_TEMPLATE=0`，即原路径；一遍用模板。按测试节点逐条比较结果。

测试文件：`tests/api/test_customer_summary.py`、`tests/api/test_customer_material_submissions.py`、`tests/api/test_project_assignments.py`、`tests/db/test_material_submission_schema.py`（含数据库降级）、`tests/api/test_customer_workspace.py`。

结果：
- **测试本身**：25 条在两条路径下全部通过，结果一致。
- **用时**：原路径 278 秒，模板 188 秒，快约 32%。单条测试越多的文件省得越多，因为每条省约 6 秒，模板只在每个会话建一次。
- **唯一的差异**是清理阶段的随机报错：两条路径各有 1 条测试在 teardown 的 `DROP SCHEMA ... CASCADE` 撞上 `max_locks_per_transaction`（OutOfMemory），落在不同的测试上，属于原来就有的问题。
- **随后修复了这个清理问题**：新增 `schema_template.drop_schema`，遇到锁上限时每批删 20 张表，再删 schema。`conftest.py` 的清理改为调用它。修复后 `test_customer_summary.py` 和 `test_project_assignments.py` 共 13 条全部通过，没有 teardown 报错，也没有新的残留 schema。
- 原始结果文件：`~/b01-tools/conftest-backup/A.xml`、`B.xml`。

## 五、回退

任选其一：

1. **临时关闭**，不改文件：运行测试前设置环境变量 `PAPERASSIST_TEST_SCHEMA_TEMPLATE=0`，就回到原来的逐条迁移路径。
2. **彻底回退**：用备份恢复 conftest，并删除新文件：
   ```
   cp ~/b01-tools/conftest-backup/conftest.py.orig backend/tests/conftest.py
   rm backend/tests/schema_template.py
   ```
   备份的 SHA-256 为 `59ef4898da2df1f9a32c345bcafab649914a106087d97502118fa35b63f8682c`，与提交 `03a272c` 中的 `tests/conftest.py` 一致，所以也可以用 `git checkout 03a272c -- backend/tests/conftest.py` 恢复。注意：工作区里有大量未提交改动，只恢复这一个文件，不要整体 checkout。
3. **清理模板 schema**（可选）：模板名可用 `python -c "from tests.schema_template import template_name; print(template_name())"`（在 `backend/` 下运行）算出，然后在测试库执行 `DROP SCHEMA <模板名> CASCADE`。如果遇到 `max_locks_per_transaction` 报错，先分批删表，再删 schema。

## 六、已知限制和注意事项

- **Windows 上要能找到 `pg_dump`、`psql`**：本机在 `C:\Program Files\PostgreSQL\18\bin`。找不到时自动走原路径，只是不提速。
- **清理锁上限已处理**：原来 `DROP SCHEMA ... CASCADE` 会随机撞上 `max_locks_per_transaction`，这是测试库残留 schema 的来源。现在遇到时会分批删表。仍建议同一时间只跑一个 pytest 进程。
- **影响面**：这是全项目共用的测试设施。Codex 收尾时跑后端全量回归，建议先用 `PAPERASSIST_TEST_SCHEMA_TEMPLATE=0` 和默认值各跑一次关键目录，确认结果一致。已写入 Codex 交接清单。
