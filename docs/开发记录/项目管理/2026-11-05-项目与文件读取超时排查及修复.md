# 项目与文件读取超时排查及修复

日期：2026-11-05。范围：本地保留验收环境；修复读取延迟，保留现有项目、文件和成果。未重新计算、未重新生成成果，未提交或推送。

## 已确认的原因

1. Dispatcher 每轮 `recover_expired → reconcile_intents` 在持有数据库 schema 全局写锁时扫描存储意图文件。采样观察到事务持续约 23 秒；每个已登录请求的 `resolve_session` 也申请同一把锁，因此普通读取被无关后台写事务阻塞。三轮接口测试中，项目和文件列表等待 21.5～22.25 秒；文件详情前端的 15 秒期限先行触发。
2. `read_file_details` 为展示任务等四项引用数量调用完整 `read_references`。该入口用于文件保留/删除核验，会读取关联成果及其来源；详情接口实测 120 秒超时。
3. 研究报告列表逐条调用详情 `get()`，对每个报告重复核验完整来源和导出文件。原项目列表实测 120 秒超时。

## 修改

- 会话解析使用当前 session 的行锁，在取得行锁后读取最新账号状态、检查过期并更新活跃时间。普通业务写事务仍保留全局写锁。偏好设置改用 `NO KEY UPDATE`，避免过期撤销审计的外键锁与偏好更新互相等待。
- 文件详情使用独立的 `metadata_summary.read_metadata_counts`，只读取当前数据库快照中的固定版本、来源 JSON 和产物/任务关联。按任务 ID 去重；保留旧作业的活跃状态、异常来源的保守计数；不会把父版本关系当成当前版本仍使用同一文件。请求内只提取一次每条记录的引用，闭包计算复用提取结果。
- 研究报告列表读取保存的内容、任务状态、成员清单和元数据；报告详情、下载继续执行完整来源和文件字节核验。
- 文件删除/重解析继续使用原完整核验路径。元数据统计不产生完整性结论或删除许可。
