## 设计与全局约束

- 沿用用户当前验收目录和 `feat/auth-project-isolation`，起点 `b9df4a4`。
- 运行连接和迁移连接显式分开，保留已有 owner 为迁移账号，新建独立 DML 运行账号。运行 URL 不得作为迁移 URL 的缺省值。迁移秘密单独保存在 gitignored `backend/.env.migrations`，应用正常配置不加载该文件。
- 迁移入口在 DDL 前核验真实连接、目标数据库/schema/角色并输出无密码、无 query 的摘要；已有外部连接也须核验，offline 仍禁止。摘要写 stderr，保留 SQLite 导入 stdout JSON 契约。
- runtime 仅 CONNECT、schema USAGE、业务表 SELECT/INSERT/UPDATE/DELETE、sequence USAGE/SELECT、版本表 SELECT；不持有 owner、DDL、TRUNCATE、TRIGGER、版本表写权限及迁移角色成员身份。未来对象由实际迁移角色在每次迁移末按 metadata 白名单显式授权并复核，不使用对任意新表的默认 DML 授权，避免版本表或非业务对象意外可写。
- 仅增加四个索引：项目 owner+更新时间+id；解释、解释任务、报告的 analysis_run_id。保留10个 JSON TEXT、6个业务时间 TEXT、12个认证 DOUBLE PRECISION 时间列的旧值与精度，不改写历史内容。
- 核验 metadata 与真实库的列、PK、FK、unique、CHECK、索引及 JSON/时间数据。资源来源链仅有单列 FK 的既有边界如实记录。
- 测试只用 `paperassist_system_test` 和每例 `pa_test_<uuid32>`；DDL 故障注入、迁移和 SQLite 导入使用迁移连接，业务仍走运行连接。保留原事务回滚及专用 schema 清理保护。
- 不修改 PostgreSQL 认证策略、不猜测管理员密码。创建角色需管理员在本机交互认证；没有管理员凭据时完成可审查脚本并明确实际分权尚未完成。
