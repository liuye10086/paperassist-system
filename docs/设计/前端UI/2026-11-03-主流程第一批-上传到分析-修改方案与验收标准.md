## 4. 修改单元 A：上传与材料实际状态

在现有上传/文件区域与分析清单中复用相同状态语义，不另建中转页。

| 实际记录 | 客户显示 | 下一步 |
| --- | --- | --- |
| 正在上传、请求结果未核实 | 上传中／核实上传结果 | 继续原批次等待或回执恢复，不再次上传 |
| `queued` / `parsing` | 已保存，等待解析／解析中 | 可填写需求；依赖该文件的分析尚不能执行 |
| 普通文件 `parsed` | 可预览；是否适合分析按用途判断 | Excel 可进入配置；报告/图片作为证据材料，不自动当数值表 |
| 普通文件 `failed` | 解析失败 | 定位原文件和现有任务恢复入口；保留原件 |
| 生信文件 `stored` | 原件已保存，待导入核对 | 进入现有生信导入，带入明确选择的原件 |
| 生信导入 `waiting_confirmation` | 等待核对确认 | 进入当前导入核对页，不能把候选当已发布数据集 |
| 已发布数据集版本 | 可选择该版本配置分析 | 保留 dataset/version 身份；处理层和方法前提仍在模块内核查 |
| 正在读取／读取失败／来源不可访问 | 正在核对／读取失败／来源不可用 | 可重读或重新选择，不能显示“材料齐全” |

不再用 `file_count > 0` 表示分析材料就绪。已有文件数仍用于数量展示；导航与材料适用性分开判断。无材料的新项目仍按现有上传顺序引导；已有上传但尚未解析完成时，允许先保存需求，等待相关材料就绪。

同项目中一个文件失败只影响使用该来源的条目；其他已具备条件的条目可继续。

## 5. 修改单元 B：需求保存后形成可操作清单

第 4 步顶部优先展示“本次分析清单”，每行包含：需求名称、关联材料及版本、当前准备状态、待补内容、一个明确的操作按钮。原有通用入口和工具区继续可用，沿用直接展示和分类切换。

清单来自当前已保存需求的 `scope_items` 与 `material_refs`；未保存草稿不改变执行清单。保存并继续时使用成功返回的需求版本；未知提交结果先沿原请求身份查证，不把失败保存当成成功。

| 已选需求 | 承接路径 | 必要选择与限制 |
| --- | --- | --- |
| 质量控制 | 表格数据概况／生信数据核对与处理 | 由已关联来源类型区分；混合或不明确时让用户选择 |
| 差异分析 | 表格组间分析／生信 comparison 计划 | 复用原配置；分组、配对、单位与尺度仍须原模块确认 |
| GO / KEGG / GSEA | 现有资源与富集工作区 | 不由一个合并勾选推断 ORA 或 GSEA；先明确方法及适用结果来源 |
| 候选对象筛选 | 现有 candidate 配方 | 使用固定比较结果，不把任意原始文件当候选结果 |
| 多组学整合 | integration 配置 | 直接定位整合类型；固定定量层、样本/对象对应由原表单及预检核查 |
| 外部证据整合 | candidate 的 evidence 配置 | 保留明确证据类型、来源和可用范围，不自动外部检索 |
| qPCR / 统计复核 | qPCR 配置／表格统计 | 首次存在歧义时明确选择，不能一律进入 qPCR |
| 结果可视化 | 对应来源的现有绘图入口 | 无适用结果时指出前置分析；导航不生成新图 |
| 分析报告与可复现材料 | 既有报告/成果包入口 | 仅承接已有入口和依赖提示；统一交付库属于第二批 |

自定义范围无可靠映射时显示“需选择分析方式”，保留原文，提供现有模块选择。未勾选具体范围时提供选择分析方式的入口，不擅自新增需求。

“本次分析清单”不是后台任务清单。准备状态只报告可验证的上传、解析、关联和配置情况；“可进入配置”不写成“可执行”或“已完成”。没有需求与运行的明确关联时，历史计划只标为“可查看/选择复用”，不自动归入本次已完成成果。

## 6. 修改单元 C：传递上下文并复用已有工作

1. 需求清单进入配置时携带需求版本、条目身份及可确定的来源。固定生信版本不得替换为最新版本；文件的原始/整理层不明确时交由现有选择器确认。
2. 唯一且用途、类型匹配的来源可预选；多个候选、混合格式或用途不清时，展示候选并让用户选择。文件名和自由文本不作为自动判断科学设计的依据。
3. 已有同项目配置、固定计划和结果优先列出供复用；只有用户明确选择新计划时才建立新草稿。仅因项目存在历史任务不能认为本次需求已处理。
4. 已打开的固定计划优先于入口默认值；已有未保存草稿优先于新预填。存在差异时展示“继续现有草稿／另行选择来源”，不静默清空或覆盖。
5. 生信原件尚未导入时，返回现有导入页；已发布版本进入版本详情/配置。原件、发布数据集、处理数据层分别保留身份。
6. 新入口信息进入现有 hash 解析与序列化白名单。刷新重新读取精确需求版本；旧链接无新增字段也继续有效。需求版本更新时提示差异，由用户决定是否采用新需求。
7. 保存需求、切页、刷新和预填只读或保存原业务对象，不自动确认方案、重算、出图、解释、导出或调用模型。
8. 第 2→3→4 步的导航判定与访问历史分离。访问过后续页面、历史失败任务或与本次来源无关的任务，都不能把缺材料条目标成就绪。保留历史详情的只读访问和仅写作项目原分支。

拟新增的承接类型，实际命名在实施时保持全链一致：

```ts
type AnalysisEntryContext = {
  requirementVersionId: string
  scopeItemId: string
}
```

来源从该项目的精确需求版本和正式来源接口读取；不把原始材料、完整配置或研究内容放进 URL。现有 `fileId`、`datasetId`、`versionId`、`processedId`、`planVersionId` 继续承担各自身份。
