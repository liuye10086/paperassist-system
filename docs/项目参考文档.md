## 一 项目定位与引用问题澄清

### 1.1 本项目实际要做什么

本项目面向生物医学、药学科研用户，提供科研数据分析、SCI 原创研究论文初稿、毕业论文初稿三个模块。用户选择 SCI 或毕业论文项目，两类项目共用数据分析和文献检索能力，并支持意见驱动的多轮修改、版本保存和 Word/PDF 导出。

核心流程是：用户提供自己的研究资料和数据，系统真实计算并绘图，组织结果和方法，查找并核实已有研究，撰写初稿并插入参考文献，最后由用户审核。SCI 模块的主体是原创研究论文，不能将它误解成仅靠文献生成综述。

**这一流程不要求建设向用户提供第三方论文全文下载的文献库，也不能因为产品收费，就推导出每引用一篇论文都要向出版社付费。**

### 1.2 正常引用与复制传播的区别

| 实际行为 | 在本项目中的含义 | 需要区分的事项 |
| --- | --- | --- |
| 用用户自己的数据绘图、写结果 | 数据分析和原创研究写作 | 图表和统计结果应来自用户资料与真实计算 |
| 阅读已有研究，用自己的表述概括发现并标注引用 | Introduction、Discussion、方法引用 | 通常不因列为参考文献而需要逐篇购买版权授权；须准确归因，不照搬受保护表达 |
| 保存 PMID、DOI、题名、作者、来源链接和引用关系 | 引用管理与核查 | 不等于保存或销售论文全文 |
| 读取摘要或获准使用的全文供模型核对 | 自动化检索与证据判断 | 按实际来源和获取方式处理；有引用不代表自动获得任意抓取、复制或传输权限 |
| 复制他人的图表、长段原文，或向其他用户提供全文 | 内容再利用或传播 | 需另看材料许可、适用例外或取得授权，不能仅靠加参考文献解决 |
| 在产品里批量展示 JIF、JCR 分区等指标 | 期刊推荐的数据服务 | 与论文里的参考文献引用是另一项功能，应按指标来源的接入及展示条件实现 |

例如，在论文中根据读到的研究写出“既有研究观察到指标 A 与结局 B 存在关联[1]”，并在文末列出文献信息，属于正常的研究归纳与引用场景。把该论文整张图、数页正文或 PDF 原样提供给其他用户，则涉及不同的使用行为。

版权通常保护具体表达，而不保护研究思想、方法本身；实际适用还取决于使用方式和法域。这里的工程结论是：正常引用不是逐篇版权采购流程，也不是任何复制行为的免责依据。参考：[美国版权局关于保护范围的说明](https://www.copyright.gov/help/faq/faq-protect.html)。

### 1.3 前述第十三、十四点应如何理解

此前把额外的全文传播场景放在核心写作流程旁边，容易造成“要做这个 Agent 就必须购买文献版权”的误解，应予纠正。

第十三点涉及的是 V0.13 的 **6.8 投稿期刊建议**：如果要接入并向用户展示影响因子和分区，需要解决对应数据源的使用条件。它不限制正常检索和引用论文，也不意味着第一版必须购买 Clarivate 服务。

第十四点涉及的是 **文献内容的获取与再利用方式**。NCBI 提醒，PubMed 摘要的权利可能属于作者或出版社；这个提醒不能被扩大解释成“列参考文献也要取得出版社授权”。[NCBI 官方政策](https://www.ncbi.nlm.nih.gov/home/about/policies/)与 [PMC 版权说明](https://pmc.ncbi.nlm.nih.gov/about/copyright/)区分了免费访问与内容再利用。

### 1.4 本项目需要保存什么

V0.13 的 6.5 要求保存候选文献信息、检索式、检索时间和来源；6.6 要求保存论述与文献的对应关系及支持依据。因此，完全不留文献记录不符合当前需求，但这与建设全文共享库有很大差别。

建议每个项目保存：PMID、DOI（有则记录）、书目信息、来源链接、检索记录、实际读取范围、核验状态、引用位置，以及用自己的话整理的支持理由。需要定位证据时记录摘要位置或全文页码；涉及原文片段时按来源条件控制必要范围。

摘要和全文按任务需要、来源条件及保留策略处理，不默认长期保存所有全文。用户上传的资料限制在相应项目内使用；上传本身也不能自动视为获得跨用户传播或任意第三方处理的授权。仅有摘要时，只能引用摘要足以支持的结论，不能编造全文细节。

## 三 数据分析模块

对应需求：5.2 文件上传、5.3 文件解析、5.5 真实计算、5.6 图表生成、5.7 解释、5.8 报告。

### 3.1 Data Formulator 的复用边界

重点研究它的数据理解、自然语言交互、数据变换、图表选择和分析过程展示。可以作为交互原型或拆取部分实现，但不能直接把通用图表能力当作完整的生物医学统计内核。

本项目还需要自己封装统计方法选择、参数校验、计算结果结构和图表规范。大模型负责理解需求、提出计划和解释；统计库负责真实计算。根据研究设计检查样本、变量类型、配对关系、缺失值和方法前提，不能让模型读一遍数据后猜测 P 值或置信区间。

### 3.2 统计计算组件

| 组件 | 主许可 | 建议职责 | 许可来源 |
| --- | --- | --- | --- |
| SciPy | BSD-3-Clause | 基础统计检验、分布与数值计算 | [LICENSE](https://github.com/scipy/scipy/blob/main/LICENSE.txt) |
| statsmodels | BSD-3-Clause | 回归、统计建模与估计 | [LICENSE](https://github.com/statsmodels/statsmodels/blob/main/LICENSE.txt) |
| lifelines | MIT | 生存分析、Kaplan–Meier、Cox 模型 | [LICENSE](https://github.com/CamDavidsonPilon/lifelines/blob/master/LICENSE) |
| scikit-learn | BSD-3-Clause | ROC、AUC 与适用的机器学习评估 | [COPYING](https://github.com/scikit-learn/scikit-learn/blob/main/COPYING) |

表格处理可另选 pandas 与 Excel 原生读取组件，绘图组件按实际图型选定；这些配套依赖需在落地时一并记录版本和许可。

森林图是结果呈现形式，不能只选一个绘图库就视为完成统计分析。应先明确展示的是回归效应量、亚组结果还是荟萃分析结果，再确定计算方法与置信区间来源。

### 3.3 文件解析应按格式分流

Docling 可用于文档布局、文字、表格和图片结构提取。Excel/CSV 的数值分析则应优先使用能够保留原始单元格、数据类型和工作表关系的读取方式，不宜先转 Markdown 后再从文本恢复数值。

统一内部结构应保留原文件、表格及字段、数值与单位、图片、正文、来源位置和解析不确定项。扫描表格的 OCR 结果、合并单元格、公式及单位尤其需要核对。Docling 的 MIT 许可不自动覆盖所有可选模型权重。

### 3.4 结果交付

每项分析保留输入版本、方法、参数、实际执行代码或工具调用记录、结构化结果与图表。图表必须带有相应标题、轴名称与单位、分组、图例、统计标记及图注，传入写作模块时保持绑定。

生成代码的执行环境应与应用服务隔离，限制文件访问、网络、时长和资源；这部分执行服务需要自行设计，不能把演示项目的代码执行方式直接当作多用户生产方案。

## 四 文献检索与引用模块

对应需求：6.5、6.6、7.5，以及修改过程中的补充文献。

建议顺序：确定论述需要的依据 → 生成关键词、同义词与 MeSH 检索式 → Bio.Entrez 调用 ESearch → 按 PMID 调用 EFetch → 去重和整理记录 → 读取可用摘要或合规获取的全文 → 核对论述支持程度 → 生成引用和参考文献列表。

Bio.Entrez 是接口实现工具；应按 NCBI 当前要求配置调用身份、限流、重试和缓存。多用户服务的总请求量需要统一控制，不能只依赖单个进程的限流。

PaperQA 可作为证据提取和文档问答候选，但它不能保证每条引用都正确，也不能代替 V0.13 所要求的验证规则。第一版候选文献量较小时，可以先实现“PubMed 检索 + 摘要核验 + 引用关联”，不必为了使用 PaperQA 就额外建设完整向量数据库或全文知识库。

无论是否引入 PaperQA，都应区分以下情况：

| 核验结果 | 系统行为 |
| --- | --- |
| 文献存在，内容支持论述 | 建立关联，按格式引用 |
| 文献存在，但只部分支持 | 收窄表述，明确适用条件 |
| 只有摘要且需要全文细节 | 提示补充全文或调整表述 |
| DOI/PMID 存在但内容不支持 | 不作为该论述依据 |
| 来源或支持关系无法核实 | 标记待核实，不编造 |

保存引用关联是为了避免错引和支持多轮修改，并不要求向用户提供原文下载。

## 五 SCI 论文模块

对应需求：6.2—6.4、6.7、6.9。

建议从 data-to-paper 研究数据追溯、科研步骤衔接和分析代码检查，再把适合本项目的流程放入统一编排层。不要直接把它当作已经具备用户、项目、计费、审稿轮次和毕业论文模板功能的 SaaS 底座。

生成顺序按内容依赖安排：先整理真实方法和结果，再组织 Results 与 Materials and methods；检索核实后写 Introduction 与 Discussion；最后提炼 Title、Abstract，并生成 References。最终输出按 V0.13 的七部分顺序排列：Title、Abstract、Introduction、Results、Discussion、Materials and methods、References。

应自行实现研究结果分组、图表引用、章节间一致性检查，以及统计结果变化后的同步更新。论文中的关键数值应能追溯到结构化结果和原始输入；引用文献中的实验和结果不能变成用户自己的研究事实。

GPT Researcher 和 STORM 可以帮助研究提纲与问题拆分，但不应把开放网页检索结果直接视为已经满足 PubMed 文献核验要求。它们的能力与自研写作流程有重叠，第一版没有必要同时引入多个完整写作框架。

## 六 毕业论文与文档导出

对应需求：7.2—7.4、7.6、7.7，并服务 5.8 和 6.7 的报告导出。

毕业论文与 SCI 写作可以共用研究资料、统计结果、文献核验和修改引擎；区别主要在章节规范、学校模板、格式规则及意见来源。无需为二者重复建设整套后端。

建议使用 python-docx 处理 Word 文档，在高层接口未覆盖的场景操作 OpenXML；有多个文档合并需求时再引入 docxcompose。学校模板解析、规范冲突处理和格式检查仍需要自研。

docxcompose 的定位是拼接文档，不是任意学校模板的自动识别或百分之百排版还原器。页眉页脚、分节、编号、目录、图表题注和交叉引用需要单独验证。

python-docx 也不直接完成 PDF 渲染。PDF 导出需要独立选择和验证转换引擎，处理字体、页码、目录更新和分页差异。不能仅把“python-docx → PDF”画成一条箭头就视为实现完成。

优先以少量真实学校模板验证端到端输出，明确支持范围，再扩大模板兼容性。中英文标题、正文、图表标签、图注和说明应随任务语言一致；学校要求的双语内容按模板处理。

## 七 期刊推荐的独立处理

对应需求：6.8。它与普通参考文献引用分开实现。

第一版可先按研究主题、文章类型、期刊收稿范围、相关发表内容、开放获取方式、已核实费用与作者指南提供候选。记录来源和核实日期，无法取得的字段标记待核实。

OpenAlex 可作为开放书目信息的候选来源，期刊官网用于核对收稿范围与投稿要求；正式接入时确认字段含义、服务条款与更新策略。不能把 PubMed 可检索或某个开放数据库的收录，等同于 SCI/SCIE 收录。

如需系统化显示 JIF、JCR 分区，应确认取得的数据使用许可覆盖具体产品的展示及再提供方式。Clarivate Journals API 明确要求付费许可，但“付费接入”不应被自动理解为获得所有对外再分发权利。中科院分区与 JCR 分区也属于不同评价体系，不能混用。

第一版可以暂不提供这些指标，保留其他期刊匹配能力。**不接入 JIF/JCR，并不妨碍实现数据分析、写论文和正常文献引用。**

来源：[Clarivate Journals API](https://developer.clarivate.com/apis/wos-journal)。

## 八 主方案排除与降级项目

| 项目 | 决定 | 准确原因 |
| --- | --- | --- |
| AI-Scientist-v2 | 排除源码引入 | 使用自定义 AI Scientist Source Code License，含用途限制及生成论文披露等条件；不符合本项目优先采用宽松许可的选型要求 |
| PandasAI 整仓库 | 不纳入第一版 | 主体与企业部分存在许可边界，不宜未经区分整仓引入；MIT 部分不是一律禁止商用 |
| STORM | 保留参考 | 许可宽松，但与既有写作规划能力重叠，暂不需要生产依赖 |
| GPT Researcher | 辅助候选 | 可用于规划，不能替代本项目规定的文献核验链路 |
| MarkItDown | 备用思路 | 第一版先验证主解析路径，避免引入重叠解析栈；如实际采用，再核对版本、许可与格式能力 |
| 小型毕业论文专用 Agent | 不选作底座 | 暂无充分依据证明其模板、版本和科研核验能力满足当前需求；不据此宣称全部不能商用 |

AI-Scientist-v2 的排除不等于认定所有商业使用都被绝对禁止；PandasAI 的排除也不等于其 MIT Core 不可商用。这些是围绕本项目需求和维护成本的取舍。

来源：[AI-Scientist-v2 LICENSE](https://github.com/SakanaAI/AI-Scientist-v2/blob/main/LICENSE)、[PandasAI 根许可](https://github.com/sinaptik-ai/pandas-ai/blob/main/LICENSE)、[PandasAI 企业许可](https://github.com/sinaptik-ai/pandas-ai/blob/main/ee/LICENSE)。实际使用时按所选版本的目录和文件声明核对。

| 6.5 文献检索 | Bio.Entrez | 检索规划、限流、去重、记录管理 |
| 6.6 引用核验 | PaperQA 候选 | 支持关系判定、核验状态、引用对应检查 |
| 6.7 SCI 初稿输出 | 编排层、Word 组件 | 章节生成、事实与数值一致性、文档输出 |
| 6.8 期刊建议 | 开放数据源、期刊官网 | 数据来源选择、匹配排序、更新及核实 |
| 6.9 审稿修改 | 共用分析、检索与写作组件 | 意见编号、修改计划、逐条回复、版本关系 |
| 7.2—7.6 毕业论文 | python-docx、OpenXML、按需 docxcompose | 模板规则、章节生成、格式冲突与排版验证 |
| 7.7 导师及评审修改 | 共用修改引擎 | 学校要求与逐条意见处理 |
| 8 项目中心 | 常规应用基础设施 | 用户项目、文件权限、成果与历史版本 |
| 9 任务系统 | LangGraph 状态与恢复能力 | 调度、队列、进度、重试策略、费用记录 |

LangGraph 可以支撑工作流状态和人工介入，但完整的后台任务队列、持久化配置、多租户权限及费用系统仍是产品工程工作，不能默认框架自动提供。

## 十 建议架构与最小实施路径

### 10.1 职责划分

| 层次 | 建议职责 |
| --- | --- |
| 产品层 | 用户、项目、任务入口、文件、版本、意见、下载、计费与后台 |
| 编排层 | LangGraph 组织分析、SCI 写作、毕业论文写作及修改流程 |
| 工具层 | 文件解析、真实统计、绘图、PubMed 检索、证据核验、Word/PDF 导出 |
| 数据层 | 原始输入、结构化结果、图表、引用关联、任务状态和稿件版本 |

这些模块是职责划分，不要求第一版全部拆成独立微服务，也不要求每个节点都是一个独立 Agent。

### 10.2 第一版的核心与可选部分

优先确定 LangGraph、原生表格读取、适用统计工具、Bio.Entrez、python-docx，以及文档解析和 PDF 转换方案。Data Formulator 与 data-to-paper 优先用来研究交互和科研流程，能否复用具体代码由小规模验证决定。

PaperQA 作为证据模块候选；GPT Researcher 与 STORM 暂不设为上线前必备。不要因为它们都与科研有关，就同时把完整项目拼入系统。

### 10.3 推荐验证顺序

1. 跑通一份真实 Excel 数据的解析、统计、带图注绘图和 Word 报告。
2. 跑通一个研究主题的 PubMed 检索、摘要核验和可追溯引用。
3. 将结构化结果与文献依据组合成七部分 SCI 初稿，检查数值、图号与引用一致性。
4. 选一份真实学校模板验证毕业论文 DOCX 与 PDF 输出。
5. 用一轮审稿意见验证重新计算、正文联动、逐条回复和版本保存。
6. 在以上链路成立后补齐多用户任务、计费、管理后台与更广的模板支持。

研究源码的建议顺序为：LangGraph → Data Formulator → PaperQA → data-to-paper → Docling → python-docx/docxcompose → Bio.Entrez → GPT Researcher。源码研究顺序不要求等同于开发或安装顺序。

## 十一 收费产品使用开源代码的具体含义

MIT、BSD、Apache-2.0 属于可用于商业产品的宽松许可；通常不会仅因使用这些代码就要求公开整个自有产品源码。仍需履行实际许可条款，例如保留版权与许可声明、适用的 NOTICE、修改标记及相应再分发条件。

Biopython 的许可同样允许包括商业目的在内的使用，但应按其具体文件条款处理。复制开源代码片段进自己的项目，也不能忽略原有许可要求。

代码许可、模型权重许可、付费 API 服务条款以及第三方文献内容使用条件分别对应不同对象。对本项目而言，优先选定明确允许所需商业用途的实际组件即可，无需把未计划实现的“向用户销售论文全文”当成开发前置问题。

建议在引入组件时记录版本、来源、LICENSE 和实际用到的扩展，维护第三方声明文件。本文用于工程选型，不构成对所有依赖和全部使用场景的法律保证。
